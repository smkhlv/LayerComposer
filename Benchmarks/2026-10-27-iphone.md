# Story export benchmark — iPhone 16, 2026-10-27

The Suretare story variants rendered by the app's real pipeline: `StorySceneBuilder`, which uses
`SphereStoryBackground` / `AmbientGlowLayer` → `DualKawaseStoryBlur` → the rasterised `StoryForegroundView`. They are
exported through `DefaultExportStoryVideoUseCase` + `ComposerStoryVideoRenderer`. The gate:
**≤ 3 s per variant, no main-thread hitch > 50 ms.**

## Setup

| | |
|---|---|
| Device | iPhone 16 (iPhone17,3, A18), iOS 27.0.1, 60 Hz. An iPhone 14 (A15) was not measured. |
| Build | Debug (the test configuration), Xcode 27.1, `xcodebuild test-without-building` |
| Code | LayerComposer 1.0.0 inside the Suretare app. "Before" = the same tree with the benchmark's builder given a plain `SwiftUIStoryForeground` and no `CachingStoryForeground`, ink sharing or memos. |
| Video | 300 frames, 1080×1920, H.264 10 Mbps, `.tenSeconds` |
| Content | `item` (asset photo), `collection`, `longPost` (6 lines plus a photo, hits the 3:5 clamp), `textPost` (no media) |

Columns of `testStoryExports`:
- `wall_s`: the whole export, scene build included.
- `scene_s`: `makeScene` alone.
- `peak_footprint_MB` / `delta_MB`: `phys_footprint` sampled every 2 ms (absolute, and above the value at the start).
- `max_main_stall_ms`: the longest the main thread did not answer a ping from a background thread.

The `previews` rows build the carousel's three scenes in one go, as the Share sheet mounts (`ComposerPreviewView`
builds its scene when it attaches to the window, and the carousel is an eager `HStack`). Each content runs its
previews first and then its three exports, as the app does. There are 3 rounds.

The numbers come from the Suretare app's own device benchmark, which is not part of this package. The package's
own benchmark (`ExportBenchmarkTests`, `COMPOSER_BENCH=1 swift test`) measures LayerComposer alone on a Mac; its output
is below.

- **First video after launch.** It carries about 0.9 s of warm-up: H.264 session and pipeline creation, off the main
  thread. It took 2.76 s here (2.80 s and 2.91 s in two earlier runs with the cache) and 3.47 s "before", which is
  the only time the 3 s gate was exceeded. Later videos took 1.84–1.95 s.
- **Memory.** A video export adds about 90–100 MB to the footprint while it runs; the first adds 300–400 MB. A photo
  export adds about 45 MB. The peak footprint in the test host was 455–475 MB, with 690 MB for the first video.
- **Scene build during an export.** It went from 28–82 ms to 1–18 ms: the export now reuses the foreground its preview
  rasterised.

4. the card image load;

- **Reopening the same post.** The previews now take about 5 ms, because the cache still holds both foregrounds.
- **Remaining stall.** The 54–64 ms that is left is the window snapshot and the blur levels, back to back.
- **Prepare.** It reads from the disk cache off the main thread. Runs 1–2 waited 240–850 ms for it; runs 3–5 took
  about 1 ms. Runs 1–2 most likely wait behind the fixture's own disk writes on SDImageCache's IO queue. This was not
  investigated further: it is latency before the sheet appears, not a hitch. In the app, the feed has usually just
  shown the photo.

## Profile (Instruments Time Profiler, in-app hook, `xctrace record --launch`)

- **Before.** The main thread's long stretches during an export came from `StorySceneBuilder.makeScene`:
  - `SwiftUIStoryForeground.makeForeground`, made of `ForegroundRasterizer` (`ImageRenderer`) and
    `UIImage.pngData()` (`PNGWritePlugin::writePNG`, about 11 ms);
  - `SwiftUIStoryForeground.cardAspectRatio` (about 17 ms, posts only);
  - `StorySceneBuilder.averageHex` (about 10 ms, posts only).

  The frame loop itself (`ComposerFrameEncoder`, writer back-pressure) never held the main thread long.
- **After `CachingStoryForeground`.** Item exports' `makeScene` took 2–5 ms. A second trace still showed the long post
  missing the cache in rounds 2–3 (74–84 ms): the first cache, an `NSCache` with `countLimit` 3, was evicting the
  story's own entries. It was replaced with an exact least-recently-used list.

## Tuning (app side; LayerComposer itself is unchanged)

1. **`CachingStoryForeground`** wraps `SwiftUIStoryForeground` in `StoryShareModule`:
   - one foreground per story, ink and layout, keeping the 3 most recently used (about 8 MB each);
   - the last card's measured aspect ratio.

   The exports reuse the carousel's work.
2. **Ink sharing.** `StoryVariant.foregroundInk`: darkSpheres and ambient both draw light ink, so they share one
   foreground. The carousel now rasterises 2 foregrounds, not 3.
3. **One-entry memos.** One for the card's PNG (`SwiftUIStoryForeground`) and one for the cover's average colour
   (`StorySceneBuilder`), both keyed by the `UIImage` instance.

Not tuned, because the data did not point there:
- the per-frame `TexturePyramid`;
- writer back-pressure: on the Mac, static and animated backgrounds export in the same time, so the encoder is the
  bound;
- the first-export warm-up: it is inside the encoder, off the main thread, and within the gate.

## Package benchmark, macOS (M1 Pro, macOS 27.0.1)

`COMPOSER_BENCH=1 swift test --filter ExportBenchmark` uses a copy blur, so it measures the composer and the writer
alone. The XCTest `measure` averages were:
- videos: 1.566 s and 1.576 s;
- the still: 0.007 s;
- peak physical memory: 171 MB per video, 71 MB for the still.

```
COMPOSER_BENCH ambient-still device=Apple M1 Pro frames=300 wall s (first is warm-up): 0.271 0.009 0.007 0.006 0.007 0.007
COMPOSER_BENCH ambient-video device=Apple M1 Pro frames=300 wall s (first is warm-up): 1.854 1.580 1.584 1.593 1.585 1.604
COMPOSER_BENCH static-video device=Apple M1 Pro frames=300 wall s (first is warm-up): 1.613 1.602 1.594 1.590 1.605 1.603
```
